# FastPassword v2 算法规范

> 版本：v2.1.0 ｜ 日期：2026-10-21（v2.1：账号进 salt，见 §4.1。**破坏性变更**——v2.0 的全部向量与密码作废）
> 初版：v2.0.0 ｜ 2026-10-18
> 状态：**已用 C# 参考实现验证过全部向量**（`_probe_argon/Program.cs`）
> 定位：**本项目唯一算法**。经确认（2026-10-18）**不实现花密 v1 兼容模式**——用户无存量花密账号。
> 花密算法仅作为设计背景保留在计划文档 §1。

---

## 0. 一句话设计

用 **Argon2id 作为确定性 KDF**，把「主密码 + 站点标识 + 参数」映射成一段高熵字节，再无偏映射到 62/70 字符集。
相比花密：工作因子从「1 次 HMAC-MD5」提升到「64 MiB 内存 + 3 轮」，字符集从「16 个 hex」扩展到「62/70 个」。

---

## 1. 设计目标与非目标

### 目标

| # | 目标 | 达成方式 |
|---|---|---|
| G1 | **抗暴力破解** | Argon2id，64 MiB 内存硬性，单次约 180 ms |
| G2 | **确定性** | 无随机数；同输入永远同输出 |
| G3 | **无状态** | 不存 salt、不存密码；只存「站点 + 参数」 |
| G4 | **字符集可用** | 62 档（纯字母数字）/ 70 档（62 + `!@#$%^&*`） |
| G5 | **长度可配** | 12–32，默认 16 |
| G6 | **域分离** | 站点标识不同 → 输出完全无关 |
| G7 | **可版本化** | 版本号进 KDF 输入，v3 可与 v2 共存 |

### 非目标

- ❌ **不兼容花密 v1**。需要沿用旧密码的场景走 Legacy 模式（独立算法，见 §11）。
- ❌ **不抵抗「定向爆破」**。见 §10 已知局限。
- ❌ 不做密码存储、不做同步、不联网。

## 2. 参数（v2 固定）

| 参数 | 值 | 说明 |
|---|---|---|
| KDF | Argon2id（RFC 9106） | 混合模式，抗侧信道与抗 GPU 兼顾 |
| `m` 内存 | **65536 KiB**（64 MiB） | 单次分配，不可下调 |
| `t` 迭代 | **3** | |
| `p` 并行度 | **1** | 固定为 1，保证跨机器输出一致 |
| 输出长度 | **32 字节** | 256 bit，供字符映射使用 |
| `length` 密码长度 | 12–32，**默认 16** | 进 salt |
| `charsetId` | **默认 1**（70 档，含 `!@#$%^&*`）/ 0（62 档，纯字母数字） | 进 salt |
| `strict` 类别保证 | **固定 true（不可配）** | 进 salt；界面不暴露 |
| 版本前缀 | `"FastPassword/v2"` | 进 salt |

**已确认的默认值**（2026-10-18）：`length=16`、`charsetId=1`、`strict=true`。

> **`strict` 已固定为 true，界面不再暴露**（2026-10-19 决定）。
> 原因：它参与 salt 派生，做成开关等于给用户一个"一键让所有旧密码失效"的按钮——
> 同一站点切一次开关就得到完全不同的密码，且不可恢复。
即新站点默认产出 16 位、大小写+数字+经典符号、熵约 **98.1 bit** 的密码。

> `charsetId=1` 曾短暂定义为 25 符号的 87 档，**从未发布**，现已重新定义为 70 档。旧 87 档的测试向量全部作废。

**实测耗时（本机，单核）**：179 ms（p=1）/ 105 ms（p=4）。
**不要改 `p`**：`p` 影响输出，改了所有密码作废。

## 3. 计算流程

```
输入: master  (主密码, 任意 Unicode)
      site    (站点标识 / 区分代号, 任意 Unicode)
      account (账号, 任意 Unicode, **可空**)
      length, charsetId, strict

1. siteKey    = UTF8( NFC(site) )
   accountKey = (account == "") ? 空 : UTF8( NFC(account) )
2. salt    = SHA-256( SaltInfo(siteKey, accountKey, length, charsetId, strict) )   // 见 §4
3. pwdKey  = UTF8( NFC(master) )
4. raw     = Argon2id(P=pwdKey, S=salt, m=65536, t=3, p=1, T=32)
5. alphabet = (charsetId == 0) ? C62 : C62 + SYM
6. for attempt = 0 .. 16:
       seed = (attempt == 0) ? raw
                             : SHA-256( raw || LE32(attempt) )
       cand = BaseN_Encode(seed, length, alphabet)                    // 见 §6
       if (strict == false) or Satisfied(cand, charsetId) or attempt == 16:
           return cand
7. 不可达
```

## 4. salt 派生（**这里曾经出过 bug，别改结构**）

```
SaltInfo 的字节序列（按顺序拼接，无长度前缀，靠 0x00 分隔）：

   "FastPassword/v2" 0x00
   "site"   0x00  siteKey 0x00
   "account" 0x00 accountKey 0x00        ← 空账号也写（只写标签与分隔符），见 §4.1
   "len"    0x00  LE32(length)
   "cs"     0x00  LE32(charsetId)
   "strict" 0x00  (strict ? 0x01 : 0x00)

salt = SHA-256( 上述字节序列 )        // 32 字节
```

### 4.1 账号段（v2.1，**破坏性**）

```
"account" 0x00 UTF8(NFC(account)) 0x00        ← 紧跟在 site 段之后，无条件写入
```

账号为空时写的是 `"account" 0x00 0x00`（标签 + 空 + 分隔符）——**照样占 9 个字节**，
salt 与 v2.0 完全不同。也就是说：

> **升级到 v2.1 时，v2.0 生成的所有密码全部作废。**

这条是明知的取舍（2026-10-21 定）：程序没有任何实际用户，与其背着一个"空账号要特判"的分支
（每个调用点都要想清楚"这里到底传没传账号"），不如让"账号是输入"这件事无条件成立——
**salt 的字节序列只有一种形状，读代码的人不需要知道历史**。

代价与看门：

| 项 | 处理 |
|---|---|
| `VectorTests` 全部黄金向量 | 已按 v2.1 重算并冻结（本机实现产出） |
| `AlgorithmSelfCheck.ExpectedVectorHash` | 已同步更新（基准密码 `6^!SqgGqlSPAkG8*`） |
| 跨实现验证（C# vs libargon2） | **仅对 v2.0 布局成立**。Argon2id 本身未变，变的是 SHA-256 的输入多了一段；要重新做交叉验证需按 §4 的字节序列重跑 |

> ⚠️ **改动这一段 = 全部密码作废**。冻结向量在 `AccountDerivationTests.Vector_账号参与派生`
> （`1AB$%77ceZo7epS0` / `mo00EsGjKCOcynvE`）与 `VectorTests`。

### 为什么必须把所有参数塞进来

参考实现的第一版没这么做，结果：

```
len=16 → 5mDQSB8qlFmyiiUT
len=20 → x5Pw5mDQSB8qlFmyiiUT     ← 后 16 位完全相同
```

因为 `BaseN_Encode` 取的是大数的**最低位**，短密码天然成了长密码的后缀。站点泄露 16 位版本后，攻击者只需枚举 70⁴ ≈ 2400 万次即可得到 20 位版本，**完全绕过 KDF**。

修复后 `len=16` 与 `len=20` 的输出彻底无关。**任何影响输出的参数都必须进 salt，这是铁律。**

同理，`strict` 也进 salt：否则「先按 strict=true 生成、后来改成 false」可能得到相同或不同的密码，行为不可预测。

账号同理：两个账号在同一站点必须有不同的密码，否则"换个账号登录"这件事在密码层面根本不存在。
**注意账号不做 trim**——首尾空格会如实进入 salt，界面上只提示、不修正（与 §4 的"只拒绝不修正"一致）。

## 5. Argon2id

标准 RFC 9106 实现，无需自定义。.NET 用 `Konscious.Security.Cryptography.Argon2`（MIT，v1.3.1，已实测兼容 net10.0）。

```csharp
using var a = new Argon2id(pwdKey)
{
    Salt = salt,
    MemorySize = 65536,      // KiB
    Iterations = 3,
    DegreeOfParallelism = 1
};
var raw = a.GetBytes(32);
```

## 6. 字符集映射（无偏）

### 字符表

```
C62 = "abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789"   (62)
SYM = "!@#$%^&*"                                                       (8)
C70 = C62 + SYM                                                        (70)  ← 默认
```

**符号只取这 8 个经典符号**（2026-10-18 用户决定）。理由：`!@#$%^&*` 是几乎所有系统（含银行、老 ERP、内网系统）都接受的符号集，兼容性风险接近零。代价是熵从 103 bit 降到 98.1 bit（损失 4.7 bit，可忽略）。

**不要「把符号重复填充到某个长度」**。技术上没必要——`BaseN_Encode` 用 BigInteger 连除，对任意 base 都均匀，不需要 2 的幂或任何特殊长度。而且重复填充会造成**偏置**：若 `SYM` 重复 k 次，符号出现概率变为字母的 k 倍，熵不增加但分布变歪。直接用 70。

**为什么不再用 25 符号的 87 档**：初期版本用过 `!@#$%^&*()-_=+[]{};:,.<>?`，但 `; , . : [ ] { } ?` 在部分系统被拒绝，且`{}` `[]` 在模板/SQL/正则场景里容易出问题。8 个经典符号牺牲 4.7 bit 熵换接近 100% 的兼容性，划算。

### 映射算法

把 `seed`（32 字节）当 **大端无符号 256 bit 整数** `N`，做 `length` 次连除：

```
for i = length-1 downto 0:
    (N, r) = DivRem(N, |alphabet|)
    out[i] = alphabet[r]
```

取的是最低 `length` 位（低位对齐）。

**无偏性**：`|alphabet|` 不整除 2^256，理论上有 ≤ 2^-173 量级的偏差，工程上可忽略（远小于 62 阶乘级别的偏差）。**不要改成 `seed[i] % 62`**——那会产生 3% 量级的可见偏差。

## 7. strict 模式（字符类别保证）

很多站点要求「至少 1 个大写、1 个小写、1 个数字（+ 1 个符号）」。`strict=true` 时：

```
满足条件 = 至少1个小写 且 至少1个大写 且 至少1个数字
         且 (charsetId==0 或 至少1个符号)
```

不满足则用 `SHA-256(raw || LE32(attempt))` 作新 seed 重新映射，最多 17 次。

**为什么不直接替换字符**：随机替换会破坏位置独立性，且难以证明熵损失上界。重试法每次只需一次 SHA-256 + 大数除法（微秒级），不重算 Argon2。

**实测重试率**：

| 配置 | 需要 1 次重试 | 需要 2 次以上 |
|---|---|---|
| 16 位 / 62 档（不要求符号） | 约 6% | < 0.1% |
| 16 位 / **70 档（默认）** | **约 22%** | 约 2% |

70 档重试率高的原因：符号只占 `8/70 = 11.4%`，16 位里一个符号都没有的概率是 `(62/70)^16 ≈ 13.6%`。这是"只用 8 个经典符号"的直接代价，可接受——重试只多算一次 SHA-256（微秒级），不重算 Argon2。

**熵代价**：强制含数字使理论熵下降约 0.05 bit，可忽略。

## 8. Unicode 归一化

主密码与站点标识都做 **NFC** 后 UTF-8 编码。

```
"é" (U+00E9)  与  "e" + U+0301   → 归一化后输出完全相同（已实测 ✅）
```

**这条 v1 没做**。花密直接 `UTF8(原文)`，所以同一个视觉字符若来自不同输入法，会产生不同密码。v2 必须修掉。

⚠️ 注意：这**加强了**「与花密不兼容」——同一个中文主密码，v1 与 v2 本来就输出不同，无所谓。

## 9. 版本化规则

- 版本前缀 `"FastPassword/v2"` **必须**出现在 salt 里。
- 升级到 v3（例如 Argon2 参数升级、字符集扩展）时：
  1. 新增 `"FastPassword/v3"` 分支，**不改 v2 的任何字节**。
  2. 每个站点条目记录 `version` 字段。
  3. UI 上明确显示当前站点用的是哪个版本。
- **永远不要「原地升级」**：改了参数就改了密码，等于把所有存量账号锁死。

## 10. 已知局限（必须写进关于页）

1. **确定性 salt 无法抵抗定向爆破。** 攻击者若锁定某个站点，可对该站点的 salt 做离线字典攻击，成本 = 每次 180 ms（单核）/ 约 200–500 次每秒（高端 GPU）。
   - 8 位弱主密码：约 **200 年**（vs 花密 70 秒）。
   - 12 位随机主密码：实际上不可行。
   - **结论：主密码强度仍是第一道防线，只是现在有 8 个数量级的缓冲。**
2. **参数即状态。** 每个站点必须记录 `length / charsetId / strict / version`，否则下次算不出来。这是「灵活性」换来的代价，花密靠「永远 16 位 hex」规避了它。
3. **单次 180 ms，无法做到「输入即算」。** UI 必须防抖 ≥ 500 ms，且计算在后台线程、并发上限 1、新请求覆盖旧请求（Argon2 不支持中途取消）。
4. 每次生成分配 64 MiB 内存。单实例无压力，但**不要**在 UI 线程同步调用。

## 11. 与花密 v1 的关系（不实现，仅作背景）

| | 花密 v1 | FastPassword v2 |
|---|---|---|
| KDF | HMAC-MD5 ×3 | Argon2id 64 MiB / t=3 |
| 工作因子 | **1 次哈希** | ~180 ms + 64 MiB |
| 输出熵上限 | 64 bit（16 位 hex） | **98.1 bit**（16 位，70 档）/ 95.3 bit（62 档） |
| 字符集 | `0-9a-fA-F` + 首位 `K` | **62 / 70** |
| 长度 | 固定 16 | 12–32 |
| 类别保证 | 无 | strict 模式 |
| Unicode 归一化 | ❌ | ✅ NFC |
| 8 位主密码爆破 | 70 秒 | ~200 年 |

**决定：不实现 v1。** 用户在 2026-10-18 确认没有存量花密账号，因此：

- Core 只保留一套算法，不需要版本路由，不需要「兼容模式」开关。
- 不需要「每站点记录算法版本」这一个状态维度。
- `reference/` 下的花密 JS 快照仅作历史记录，不参与编译、不产生代码依赖。

**代价**：一旦以后发现有站点在用花密生成的老密码，得临时补一套 v1。这个可能性存在但很低，届时可以独立做一个转换工具，不必污染主程序。

```

```

### 必测边界

- `length` = 12 与 32
- `charsetId` = 0 与 1
- `strict` = true / false（验证两者输出不同）
- 空站点 `""`（允许，但要验证不崩）
- 超长主密码（1000 字符，验证 Argon2 对长 key 的行为）
- emoji 主密码（4 字节 UTF-8）
- 组合字符 `é` 的两种表示（必须输出相同）
- 大小写不同的站点（`GitHub.com` ≠ `github.com`，已验证）
- **长度后缀回归**：`len=16` 输出不得是 `len=20` 的后缀

## 13. 实现要求

> **完整实现契约见 [`核心算法稳定性保证.md`](核心算法稳定性保证.md) §3（12 条硬规则）。** 下表只是索引。

| 项 | 要求 |
|---|---|
| 依赖 | `Konscious.Security.Cryptography.Argon2` **1.3.1（精确版本）**，MIT；必须启用 `packages.lock.json` |
| 归一化 | `s.Normalize(FormC)`，**必须捕获 `ArgumentException`**（U+FFFE 等会抛） |
| 编码 | `new UTF8Encoding(false, throwOnInvalidBytes: true)` **严格模式**，禁止 `Encoding.UTF8` 默认实例 |
| 大整数 | `System.Numerics.BigInteger`（`isUnsigned: true, isBigEndian: true`） |
| 字节序 | 一律 **LittleEndian**，用 `BinaryPrimitives`，不用 `BitConverter` |
| 字符判定 | 只用 `char.IsAsciiDigit` / `IsAsciiLetterLower` / `IsAsciiLetterUpper`；比较用 `StringComparison.Ordinal` |
| 线程 | 异步 + 并发上限 1；UI 防抖 ≥ 500 ms |
| 内存 | 每次 64 MiB，算完立即释放；`raw` / `pwdKey` / `salt` 用 `CryptographicOperations.ZeroMemory` 清零 |
| 超时 | 计算超过 2 s 视为异常（低端机上 `m` 可能撑不住），**给降级提示而非换参数** |
| 启动自检 | 异步跑 Argon2 向量 + NFC 指纹，不匹配则告警（见稳定性文档 §4） |

**已验证过的三件事，写代码时不要"优化"掉**：

1. `p=1` 是硬编码常量，不是配置项。改成 4 会换掉所有密码（实测）。
2. Argon2 版本必须是 v19（0x13）。v16 输出不同（实测）。
3. `MemorySize` 单位是 **KiB**，65536 = 64 MiB（与 libargon2 交叉验证确认）。

|---|---|---|
| 默认长度 | **16** | **98.1 bit**（70 档），够用 |
| 默认字符集 | **70 档**（62 + `!@#$%^&*`） | 兼容性风险接近零 |
| 默认 strict | **true** | 保证大小写+数字+符号齐全 |
| v1 兼容模式 | **不实现** | 无存量账号 |

### 符号选择的取舍（已定）

初期考虑过 25 符号的 87 档，最终砍到 8 个经典符号 `!@#$%^&*`。理由：

| | 87 档（25 符号） | **70 档（8 符号）** |
|---|---|---|
| 熵（16 位） | 103.1 bit | 98.1 bit（−4.7） |
| 符号占比 | 28.7% | 11.4% |
| strict 重试率 | < 1% | 约 22% |
| 被老系统拒绝的概率 | **中**（`; , . : [ ] { } ?` 常被拒） | **极低** |

用 4.7 bit 熵和 21 个百分点重试率，换接近 100% 的字符兼容性——这笔账划算。重试只多算一次 SHA-256，用户完全感知不到。

**仍然存在的唯一场景**：少数站点要求"密码只能字母数字"。此时切 **62 档**（`charsetId=0`）重新生成，需要在站点上重置一次密码。**不要为了个别站点改全局默认**——那会让其他所有站点失效。
