## 一、执行摘要

| 维度 | 结论 |
|---|---|
| 架构分层 | ✅ 清晰。Core（算法/加密）/ Storage（持久化）/ App（UI）职责边界干净，无循环依赖 |
| 算法正确性 | ✅ 通过。同输入必同输出、跨站/跨账号隔离、NFC 等价输入归一，均实测正确 |
| 加密设计 | ✅ 扎实。Argon2id 64MiB/t=3/p=1 + HKDF 用途分离 + AES-GCM + AAD 绑定记录 ID，参数错误全部收口 |
| 性能 | ⚠️ 派生层优秀（198 ms / 次，符合设计）；**UI 线程存在同步 SQLite 落盘** |
| 安全性 | ❌ **发现 2 个严重问题**：明文记忆密码写入日志、退出时剪贴板不清除 |
| 数据安全 | ❌ **发现 1 个致命问题**：备份密钥轮换可用错误口令把保险库永久锁死 |
| 并发正确性 | ❌ `TryAdd` 重复检测存在 TOCTOU 竞态，实测可写入重复记录 |
| 测试 | ⚠️ 112 个测试全绿，但**覆盖不到已发现的严重问题**（全是 happy path） |
| 整体 | 代码质量明显高于同类项目，注释密度与设计意图记录优秀；但**安全承诺与实现存在背离**，且部分契约漏洞可导致用户数据不可恢复 |

**关键判断：这不是"能跑就行"的项目，而是"设计很认真但边界没测到"的项目。** 最危险的三条都不是算法问题，而是「把 A 传给 B 时忘了验证 A」这类契约漏洞——它们绕过了全部现有测试。

## 二、致命级（Critical）：可导致数据永久丢失

### 🔴 C-1 备份密钥轮换不校验记忆密码 → 保险库可被永久锁死

**位置**：`src/FastPassword.Storage/VaultStore.cs:345`（`TryRegenerateRecoveryKey`）

```csharp
public bool TryRegenerateRecoveryKey(string master, out string recoveryKey, out string error)
{
    // ← 全程没有任何 VerifyCheck：传什么口令就包裹什么口令
    byte[] kek = VaultCrypto.DeriveRecoveryKek(recoveryBytes, salt);
    recovery = VaultCrypto.SealRecovery(kek, Encoding.UTF8.GetBytes(master));
    ...
}
```

**独立探针实测结果**：

```
[A1] 错误口令 => ok=True, err=''                    ← 传错口令也返回成功
[A2] 新密钥恢复 => False, err='备份密钥正确，但保险库打不开：记忆密码不正确。'
[A3] 旧密钥恢复 => False, err='备份密钥不正确。'      ← 旧密钥已被作废
```

**触发路径**：用户已解锁 → 设置窗点「重新生成备份密钥」→ `MainViewModel.cs:603` 把 `_master` 传下去 → 用户输入错误口令 → 旧密钥立即作废 + 新密钥包裹的是错口令 → **两条路都打不开，全部记录永久不可恢复**，唯一出路是删库重建（丢失所有记录）。

**为什么现有测试没抓到**：`VaultStoreTests.cs:249-266` 只测了传对口令的正常路径。

**修复**：在包裹前加一道校验——

```csharp
if (!VaultCrypto.VerifyCheck(_keys.CheckKey, ReadCheckBox()))
{
    error = "记忆密码不正确，备份密钥未更新。";
    return false;
}
```

**附带修复**：旧密钥作废应与新密钥写入在同一事务内完成（当前已是事务，但缺少前置校验）。

### 🔴 C-2 `TryUnlock` 空口令抛未捕获异常，绕过「返回 false」契约

**位置**：`src/FastPassword.Storage/VaultStore.cs:245`

```csharp
catch (Exception ex) when (ex is SqliteException or IOException or UnauthorizedAccessException)
```

**探针实测**：

```
[B1] 未捕获异常穿透 TryUnlock: ArgumentException: Argon2 needs a password set (Parameter 'password')
```

`VaultCrypto.DeriveKeys` 在空口令时抛 `ArgumentException`（来自 Konscious 库），而 `TryUnlock` 的 catch 白名单不含它，异常直接穿透。

**影响**：`TryUnlock` 的契约是「返回 false + 错误文案」，实际却可能抛异常。当前 UI 侥幸没炸，因为 `MainViewModel.cs:378` 有 `input.Length == 0` 提前 return——**是调用方的偶然防御掩盖了库的契约漏洞**，任何新调用方直接 `TryUnlock(dir, "")` 就会崩。

**修复**：catch 白名单加 `ArgumentException`，或干脆改成 `catch (Exception ex) when (ex is not OutOfMemoryException)`。

## 三、严重级（High）：安全承诺被违背

### 🔴 S-1 明文记忆密码被写入磁盘日志

**位置**：`src/FastPassword.App/ViewModels/MainViewModel.cs:309` + `:561`

```csharp
private void ReportError(string message)
{
    AppLog.Warn(message);        // :309 ← 无条件落盘，无脱敏
    MessageRequested?.Invoke(message);
}

// :561
ReportError(
    "已用备份密钥解锁。\n\n你的记忆密码是：\n" + master +   // ← 明文记忆密码
    "\n\n请重新记下它……");
```

**为什么是严重问题**：`AppLog.Write`（`Diagnostics/AppLog.cs:63`）把消息原样 `File.AppendAllText` 追加到 `%LOCALAPPDATA%\FastPassword\logs\app.log`。这**直接违背程序自己写下的两处承诺**：

- `AppLog.cs:8-9`：*"绝不记任何用户输入（记忆密码、代号、账号、生成的密码都不进日志）"*
- `docs/使用说明.md:165`：*"本地日志……**不记任何输入**"*

**触发路径唯一且必然**：用户忘记记忆密码 → 输入备份密钥 → 恢复成功 → **明文记忆密码永久留在磁盘**。用户完全无感。

**修复**：`AppLog` 只接受结构化字段（level / code / duration / fingerprint），面向用户的文案一律不进日志；`ReportError` 改为只记一个分类标签。

### 🔴 S-2 退出程序时剪贴板里的密码永不清除

**位置**：`src/FastPassword.App/MainWindow.xaml.cs:888-911`（`ExitApplication`）

```csharp
private void ExitApplication()
{
    _exitRequested = true;
    _autoLockTimer.Stop();
    ...
    _tray?.Dispose();
    _hotkey?.Dispose();
    _hook?.Dispose();
    Close();                    // ← 全程没有 _clipboard.ClearPendingSecretNow()
}
```

**对比**：锁定路径做对了（`:514` 有 `_clipboard.ClearPendingSecretNow()`），**退出路径漏了同一句**。

**触发路径**：复制站点密码（30 秒倒计时刚起）→ 30 秒内点托盘「退出」→ **密码永久留在剪贴板，Win+V 历史里那条也永久留着**（`TryRemoveFromHistory` 同样依赖进程存活）。与 `docs/使用说明.md:110-112` 的承诺直接冲突。

**修复**：`ExitApplication` 中 `Close()` 之前调用 `ClearPendingSecretNow()`。注意它是 fire-and-forget 的 async，建议给 `ClipboardService` 加一个**同步**的 `ClearNow()`（`Clipboard.GetContent()` + 比较 + `Clipboard.Clear()`）。

### 🔴 S-3 确认框被隐藏到托盘后，程序级对话框门永久占用

**位置**：`MainWindow.xaml.cs:473`（占用）/ `:490-493`（释放）/ `:835`（`HideToTray`）

```csharp
await _dialogGate.WaitAsync();     // :473 无超时、无取消
try { ... return await dialog.ShowAsync() == ...; }
finally { _dialogGate.Release(); }  // :492 只有 ShowAsync 正常结束才执行
```

**为什么是 bug**：WinUI 3 的 `ContentDialog` 是**窗口内容里的 Popup，不是独立 HWND**。一旦 `AppWindow.Hide()`，对话框随之不可见，而 `ShowAsync()` 仍在等用户点击 → 永不返回 → `finally` 永不执行 → `_dialogGate`（容量 1）**永久持有**。

**触发场景**（都很日常）：开启「失焦自动隐藏」→ 点「删除所选」→ 确认框弹出 → 点一下别的应用 → 主窗失焦 → `HideToTray()` → 确认框连同主窗消失。

**后果不是"这次删除没成功"，而是永久性降级**：`_dialogGate` 被占死后——
- `ShowMessageAsync` 的 `WaitAsync(0)`（`:439`）永远失败 → **所有错误提示被静默丢弃**（含"写盘失败"这类数据丢失风险消息）
- `ShowConfirmAsync`（`:473`）永远排队 → **「删除记录」「覆盖确认」「重置保险库」的确认框再也不出现**，用户按下去像坏了

**修复**：
1. `HideToTray()` 前检查是否有对话框在显示（加 `_dialogOpen` 标志），有则不隐藏
2. 弹对话框期间置 `_suppressHide = true`，纳入现有抑制机制
3. `WaitAsync` 加超时 + `CancellationTokenSource`（窗口关闭时取消）

### 🟠 S-4 托盘退出时在窗口子类回调内部卸载子类（重入）

**位置**：`MainWindow.xaml.cs:908`（`_hook?.Dispose()`）

**完整调用链（已逐层核实）**：

```
WindowMessageHook.OnMessage (Interop/WindowMessageHook.cs:41)   ← 正处于 comctl32 子类链回调中
 └─ handler.GetInvocationList() → TrayService.HandleMessage (TrayService.cs:118)
     └─ ShowMenu (TrayService.cs:142)
         └─ ExitRequested?.Invoke() (TrayService.cs:176)
             └─ MainWindow.ExitApplication (MainWindow.xaml.cs:888)
                 └─ _hook?.Dispose() (MainWindow.xaml.cs:908)
                     └─ RemoveWindowSubclass (WindowMessageHook.cs:74)  ← 重入
```

MSDN 不建议在子类过程内部调用 `RemoveWindowSubclass`（该调用会移除并重排子类链，而当前正在遍历它）。更糟的是随后 `Close()` 销毁 HWND，等子类过程返回时 comctl32 还要在**已销毁的窗口**上走完剩余的链。

**后果**：用户最常走的退出路径（托盘右键 → 退出）上出现**随机崩溃**，且异常发生在原生回调里，无堆栈可查。

**修复**：把 `_hook?.Dispose()`（及 tray/hotkey）推到 `DispatcherQueue` 的下一轮执行，确保当前子类调用已返回。

## 四、中等（Medium）

### 🟠 M-1 `TryAdd` 重复检测存在 TOCTOU 竞态

**位置**：`VaultStore.cs:419-428`（`IndexOf` 检查与 `TryPersist` 之间无锁）

**探针实测**（8 线程并发添加相同「代号 + 账号」但不同 Id）：

```
[C2] round=0 成功=6 内存条数=6 不同(代号+账号)组合=1   ← 应只有 1 条
[C2] round=1 成功=6 ...
[C2] round=2 成功=5 ...
```

每轮都有 5~6 条重复记录同时落库。这违背 `VaultStore.cs:401-402` 的核心承诺"绝不在『代号+账号』冲突时静默覆盖"。

**注意**：当前 UI 路径是单线程串行调用，**实际触发概率低**；但这是库层契约漏洞，任何将来的批量导入/后台写入都会立刻踩中。测试套件两处 `DisableTestParallelization = true`（`AssemblyInfo.cs:4-5`）恰好掩盖了这个盲区。

**修复**：用 `lock` 保护 `IndexOf` + `TryPersist` 组合，或改用 `Dictionary` 键索引。

### 🟠 M-2 `TryOverwrite` 绕过「代号 + 账号」冲突检查

**位置**：`VaultStore.cs:470`（对比 `TryUpdate` 的 `IndexOf` 检查在 `:457`）

**探针实测**：

```
[D1] TryOverwrite 撞车 => ok=True, err=''    ← TryUpdate 在同场景会拒绝
```

`TryOverwrite` 只检查 Id 存在，不检查新「代号+账号」是否与另一条撞车。存储层无防线。

### 🟠 M-3 `TryRemove` 删除不存在的 Id 返回 `true`

**位置**：`VaultStore.cs:492`

**探针实测**：

```
[E1] 删除不存在的 Id => ok=True, err='', 条数=1
```

调用方无法区分"删掉了"和"本来就没有"。

### 🟠 M-4 `SettingsStore.Load` 把瞬时 IO 失败当文件损坏，丢掉用户设置

**位置**：`src/FastPassword.App/Services/SettingsStore.cs:77-82`

```csharp
catch (Exception)                    // ← 捕获所有异常
{
    TryPreserveBrokenFile();          // → File.Move(FilePath, FilePath + ".broken", overwrite: true)
    return new AppSettings();
}
```

类注释（`:47-48`）写的是"**只有 JSON 语法/类型真的坏掉时**才保留副本，瞬时 IO 错误不动用户文件"，但代码把 `IOException`（杀毒软件/同步盘短暂占用）、`UnauthorizedAccessException` 全归为"文件损坏"。

**后果**：Windows Defender 正在扫描 `settings.json` → 用户的全部设置被改名成 `settings.json.broken` → 主题、剪贴板时长、防截屏、托盘行为全部回默认。且注释说"把默认值写回去"但代码没做这一步，下次启动会再走同一条路。

**修复**：按异常类型分流——`JsonException` 才保留副本，`IOException`/`UnauthorizedAccessException` 直接返回默认值不动文件。

### 🟠 M-5 `_suppressHide` 一个 bool 承担三种互不相干的职责

**位置**：`MainWindow.xaml.cs:59`（字段）、`:124-125`（托盘菜单）、`:333`/`:323`（设置窗）、`:613`/`:603`（录入窗）

| 录入窗打开 | `:613` | `:603` |

**触发场景**：打开设置窗（true）→ 不关它，直接右键托盘图标（true）→ 点菜单外关闭（**false**）→ 主窗因失焦触发 `HideToTray()` → **主窗在设置窗还开着的情况下凭空消失**。

**修复**：改成位掩码计数器 `int _suppressHideReasons`，进入 `|=`，退出 `&= ~`。

**位置**：`MainWindow.xaml.cs:439-443`

### 🟠 M-7 SQLite 写入在 UI 线程同步执行（阻塞 IO）

**位置**：`MainViewModel.cs:832`（`TryAdd`）、`:855`（`TryOverwrite`）、`:873`（`TryRemove`）、`:955`（`TryUpdate`）、`SettingsWindow.xaml.cs:146`

`VaultStore` 关闭了连接池（`Pooling = false`）+ `PRAGMA synchronous = FULL` + WAL，每次写入都要**真实 fsync 落盘**，且这些调用全部在 UI 线程同步执行。

项目对 Argon2 的 198 ms 都用 `Task.Run` 仔细挪到了后台（`MainViewModel.cs:410,521,1242`），唯独 SQLite 落盘留在了 UI 线程。在机械盘或被 AV 实时扫描时会表现为"点保存后窗口顿一下"。

### 🟠 M-8 热键唤回窗口缺 `Activate()` 与 `FlashWindowEx` 兜底

**位置**：`MainWindow.xaml.cs:854-866`

`AppWindow.Show()` 只负责显示**不抢前台**；`SetForegroundWindow` 的返回值被丢弃，在前台锁下会失败。`花密.NET10桌面版-开发计划.md:346` 明确承诺的 `FlashWindowEx` 兜底**没有实现**。

### 🟠 M-9 `TrayService.LoadTrayIcon` 可能返回已销毁的图标句柄

**位置**：`Services/TrayService.cs:107-115`

当 `small[0] == 0 && large[0] != 0` 时，`largeIcon` 被 `DestroyIcon` 销毁（`:112`），随后 `return smallIcon != 0 ? smallIcon : largeIcon`（`:115`）**返回了那个刚被销毁的句柄**。GDI 句柄号会被系统很快复用，托盘上可能显示别的程序的图标，或 `NIM_ADD` 直接失败。

### 🟠 M-10 `async void` 事件处理器异常直达未处理异常 → 进程终止

**位置**：`MainWindow.xaml.cs:426`、`:584`、`:619`、`:645`、`:145`

`ContentDialog.ShowAsync()` 在窗口销毁 / XamlRoot 失效时抛 `COMException`，从 `async void` 逸出 → `Application.UnhandledException`（`App.xaml.cs:17`）**只记日志、不设 `e.Handled = true`** → 进程终止。

**触发场景**：删除确认框弹出时从托盘点「退出」→ 窗口销毁 → `ShowAsync` 抛异常 → 退出过程中崩溃。

### 🟠 M-11 `WindowMessageHook.OnMessage` 的 try 包住整个 foreach

**位置**：`Interop/WindowMessageHook.cs:47-61`

### 🟠 M-12 `AppLog` 轮转失败会连带丢掉整条日志

**探针实测**：
